# ADR-001: Transition semantics on active-signal sets

## Status

Accepted

## Date

2026-11-14

## Context

The four sources observe values that stay "bad" for a long time: a breaching metric, an open alert
issue, an error type that keeps occurring, a noisy log group. A source that reports every poll while
the value is bad would wake the agent every check and defeat the pre-model gate. The sibling
`compozy-jira` source solved the same problem for JQL with a full key-set diff ("newly matching"),
and that worked through review.

## Decision

Every kind maps a poll to the set of currently active keys. The engine returns only keys that are
active now and absent from the committed active set. The next committed set is
`(committed ∩ active) ∪ returned`. A key that stops being active is dropped and can be reported again
later. A fingerprint of the defining parameters triggers a quiet baseline when it changes, and
`notify_existing` opts into reporting the baseline's active set.

## Alternatives Considered

### Alternative 1: Report every poll while active

- **Pros**: simplest implementation; the agent always sees the current state.
- **Cons**: wakes the model every check during an incident; costs tokens; noise.
- **Why rejected**: defeats the purpose of a check-in source.

### Alternative 2: Time-based cool-down (report again after N minutes)

- **Pros**: periodic reminders while an incident stays open.
- **Cons**: needs per-key timestamps in state and an extra tuning knob, and blurs "new" with "still bad".
- **Why rejected**: not requested; it can be added later as an option without changing the state
  shape's meaning.

### Alternative 3: Rely on New Relic alert conditions only

- **Pros**: New Relic owns thresholds and incident lifecycle.
- **Cons**: forces operators to author alert conditions for every signal an agent watches. The
  ad-hoc NRQL, error, and log sources would lose their value.
- **Why rejected**: `newrelic/issues` covers this path; the other kinds need direct evaluation.

## Consequences

### Positive

- One engine and one state shape for all kinds, with the same semantics as the Jira source.
- Recovery is implicit, so a later "recovered" notification only needs a flag.

### Negative

- Flapping signals (active, inactive, active within minutes) wake the agent on each re-entry.
  Mitigation: the README recommends windows and thresholds with hysteresis margins. A cool-down option
  is a follow-up.

### Risks

- Capacity: a source with thousands of active keys (huge facets) fails loudly. This is intended.
